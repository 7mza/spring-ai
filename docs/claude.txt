can streaming like this be enabled for non text/primitive types, like list of objects ?

● Yes, but the media type is what determines whether it truly streams or buffers. There are two real options:

  application/x-ndjson — Newline-Delimited JSON (true streaming)

  Each object is emitted as one JSON line as soon as it's ready:

  @GetMapping("/movie", produces = ["application/x-ndjson"])
  fun movies(@RequestParam year: Int): Flux<Movie>

  Output over the wire:
  {"title":"12 Years a Slave","rating":8.1}
  {"title":"Gravity","rating":7.7}
  {"title":"Her","rating":8.0}

  curl:
  curl -N http://localhost:8080/api/prompt/movie?year=2013

  ---
  text/event-stream — Server-Sent Events

  Each object is wrapped in SSE format. Better for browser EventSource clients:

  @GetMapping("/movie", produces = [MediaType.TEXT_EVENT_STREAM_VALUE])
  fun movies(@RequestParam year: Int): Flux<Movie>

  Output over the wire:
  data:{"title":"12 Years a Slave","rating":8.1}

  data:{"title":"Gravity","rating":7.7}


  curl:
  curl -N -H "Accept: text/event-stream" http://localhost:8080/api/prompt/movie?year=2013

  ---
  What does NOT stream

  produces = ["application/json"]  // Flux<Movie>
  Spring buffers the entire Flux, collects it into a list, then sends one JSON array. Not streaming.

  ---
  The LLM catch

  At the HTTP level this all works fine. The hard part is your service layer — Spring AI's chatClient.stream()
  gives you Flux<String> of raw tokens, not Flux<Movie>. To get Flux<Movie> you have two practical options:

  1. Line-by-line parse — prompt the LLM to emit one JSON object per line, then bufferUntil("\n") and deserialize
  each line as it arrives. Fragile but truly streaming.
  2. Collect then parse — .collectList() on the token flux, join into a string, parse the full JSON array. Loses
  streaming but is reliable — this is essentially what your songs endpoint already does.

  For most LLM use cases option 2 is the right call unless you specifically need the first-token-time UX benefit.
